# ADR 0007: Cross-backend failover is not expressible in core Gateway API

- Date: 2026-08-19
- Status: accepted
- Supersedes the failover row of the design spec, section 11

## Context

The design spec promised that when the engine becomes unavailable, traffic falls
back to a smaller model, on the reasoning that a weaker answer beats no answer.
The implementation plan specified the mechanism: a second `backendRef` on the same
`HTTPRoute` rule carrying `weight: 0`, reached through retries, with the comment
"zero weight: reached only through retry, not load split".

That mechanism cannot work, and the plan's own text demanded this moment be
resolved rather than papered over: *"Either fix it or change the spec. Do not leave
a claim in the spec that no test covers."*

## What is actually true

**Weighted cluster selection happens once, and retries do not revisit it.** Envoy
selects among weighted clusters at initial route match. A retry is attempted
against a different host **inside the already-selected cluster**, never against a
different cluster. Envoy issue 5891 states it plainly, and the issue is closed
without the behaviour changing:

> "when an Envoy retries a failed request, it will retry on the same cluster in the
> list of WeightedClusters"

A backend at `weight: 0` therefore has zero probability of being selected on the
first attempt, and retries never reconsider. It is not reached at all, ever.

**A second, independent defect in the same attempt.** The retry policy was attached
with `spec.gateways: [istio-system/llm]`. That field expects an Istio-native
`networking.istio.io` Gateway. `istio-system/llm` is a Gateway API
`gateway.networking.k8s.io` Gateway, which Istio exposes internally under a
different, autogenerated name. So the policy most likely never attached to anything.
Two independent reasons for the same outcome.

**Core Gateway API has no failover primitive.** `HTTPRoute` offers weighted load
splitting and nothing else: no priority, no ordering, no health-conditioned
fallback. Genuine failover requires an Envoy-native construct — an aggregate
cluster (`envoy.clusters.aggregate`) with primary and secondary priorities, or the
two backends restructured as priority tiers of a single cluster. Both need an
`EnvoyFilter`, which is an escape hatch out of Gateway API.

## Decision

1. Remove the non-working mechanism. A manifest that looks like failover and
   delivers none is worse than no manifest, because a reader will believe it.
2. Change the spec. Section 11's failover row states that the capability is
   deferred, names the mechanism that would deliver it, and says why it is not in
   phase 1.
3. Keep the fallback `InferenceService`. A small model deployed alongside the
   primary is independently useful, and the CI overlay reuses the same pin.
4. The availability test that would have proved failover is marked skipped with
   this ADR as its reason, not deleted and not left failing. A skipped test with a
   stated reason is a record; a red test is noise, and a deleted one is amnesia.

## Cost accepted

Phase 1 has no automatic fallback. When the engine is unavailable, callers get an
error. The spec no longer claims otherwise.

## How this was found

The implementer of Task 10 wrote the manifests exactly as specified, then reported
a specific technical reason to doubt they would work, and marked the proof
unmeasured rather than asserting success. The reviewer confirmed it independently
against Envoy's issue tracker and Istio's reference documentation, and found the
second defect. Neither could run a cluster.

The plan's instruction to write the failover test before believing the feature is
what made the gap findable at all: the test named a specific observable outcome,
and asking "would this actually pass?" was enough.
